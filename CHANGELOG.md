# Changelog

## [0.3.0] - 2026-05-12

### Added

- **Tag-triggered npm publishing via `release.yml` workflow** — New `.github/workflows/release.yml` runs on every `v*.*.*` tag push (and on manual `workflow_dispatch`): checks out the tag, installs with `npm ci`, re-runs the same quality gates as CI (`build`, `check-types-pack`, `typecheck`, `lint`, `format:check`, `test`), verifies that the tag name (minus the leading `v`) matches `package.json#version` (refuses to publish otherwise), previews the tarball with `npm pack --dry-run`, then runs `npm publish --provenance --access public` with `NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}`. After a successful publish the workflow extracts the matching `## [X.Y.Z]` section from `CHANGELOG.md` (awk slice) and creates a GitHub Release with those notes via `softprops/action-gh-release@v3`; falls back to a generic "see CHANGELOG.md" body if the section is absent. A `concurrency` group `release-${{ github.ref }}` with `cancel-in-progress: false` prevents two tags from racing the publish step. (`.github/workflows/release.yml`)

The matrix targets `javascript-typescript` with `build-mode: none` (no build needed because the JS/TS analyzer reads source directly). Results surface in the repo's Security tab and on PRs. A `concurrency` group with `cancel-in-progress: ${{ github.event_name == 'pull_request' }}` ensures PRs only keep the latest analysis run while main pushes always finish. (`.github/workflows/codeql.yml`)

### Fixed

- **ESM bundle masquerading as CJS at the Node 16+ resolver** — `tsup.config.ts#outExtension` emitted the ESM bundle as `dist/index.js` and `package.json#exports.import.default` pointed at the same path. Because `package.json` does NOT declare `"type": "module"`, raw Node treats every `.js` file in the package as CJS — so a consumer running `import { useSEO } from '@hiprax/use-seo'` under `moduleResolution: "node16"` / `"nodenext"` would have Node load the ESM-syntax bundle, hit `import { useCallback, useEffect, useRef } from 'react'`, and crash with `SyntaxError: Cannot use import statement outside a module`. Bundlers (webpack / rollup / vite / esbuild) happened to paper over this by detecting ESM syntax and dispatching the file as a module, which is why the regression went unnoticed in practice — but every framework that lets Node resolve the entry first (Next.js server components, Remix server build, plain `node script.mjs`) was a ticking bomb. Now the ESM output is emitted as `dist/index.mjs` (forces Node to treat it as ESM regardless of `"type"`), `package.json#module` and `exports.import.default` updated to match, and the new `check-types-pack` gate (4/4 green: `node10`, `node16 (from CJS)`, `node16 (from ESM)`, `bundler`) keeps this regression from ever recurring. The CJS side (`.cjs` + `exports.require.default` + `cjsDefaultExportInterop` tsup plugin) is structurally unaffected. (`tsup.config.ts`, `package.json`)

## [0.2.5] - 2026-05-12

### Fixed

- **`getCurrentSEO()` cross-runtime shape divergence (`structuredClone` preserved `undefined` keys, JSON fallback dropped them)** - The previous implementation used `structuredClone(snap)` on the primary path with a `JSON.parse(JSON.stringify(snap))` fallback. `structuredClone` preserves keys whose value is `undefined`; `JSON.stringify` strips them. Because the hook's internal snapshot always seeds EVERY destructured prop (many `undefined` when the user didn't pass them), two consumers running on different runtimes would see different `'X' in result` answers for the same internal state — Node 17+ would expose `someKey: undefined`, older runtimes would show no `someKey` at all. The hook now ALWAYS uses the JSON round-trip path. The result shape is identical across every supported runtime: keys with `undefined` values are dropped uniformly. The schema requirements (no `Date`/`Map`/`Set`/`BigInt`/functions/circular refs) are documented in the JSDoc and met by `SEOProps` by construction. (`src/useSEO.ts`)
- **`getOrCreateMeta`/`getOrCreateLink` dedup loops leaked references into the caller's tracking Set** - When `preventDuplicates: true` (or `unique: true` for links) found N>1 matching elements, the helper removed elements [1..N-1] from the DOM but never propagated those removals to any caller-side `Set<Element>` used for `clearSEOTags()`. If a previous render had added the now-removed duplicates to its tracking Set, those references lingered as detached DOM nodes that GC could not collect (a small, bounded leak — typically only ONE element per dedup event per hook instance lifetime, only triggered on the first render when user-authored duplicates exist). Both helpers now accept an optional `trackedElements?: Set<Element>` parameter (matching the existing `removeMarkedElements` pattern); when provided, the dedup loop also `delete()`s removed elements from the Set. The internal `updateMetaInternal` and `updateLinkInternal` callbacks in `useSEO.ts` now thread `addedElements.current` through. Backwards-compatible: omit the parameter to keep the previous behavior. (`src/utils/dom.ts`, `src/useSEO.ts`)

## [0.2.4] - 2026-05-12

### Fixed

- **`formatTitle` template substitution mangled titles containing `$&`/`$1`/`$<x>` etc.** - The two template branches in `src/utils/title.ts` used `template.replace('{title}', trimmedTitle)` and `template.replace(/%s/g, trimmedTitle)`. `String.prototype.replace` interprets a STRING replacement's `$&`, `$\``, `$'`, `$1`, and `$<name>` tokens as backreference patterns — so a title that legitimately contained those tokens would be silently rewritten (e.g. `formatTitle('$&', { template: 'Site - %s' })` produced `Site - %s` because `$&` expanded to "the entire match", which IS the placeholder string). Both branches now use `template.split(placeholder).join(trimmedTitle)`, which performs a literal substitution with no special-character processing. As a side-effect of the change, the `{title}` branch now replaces ALL occurrences of `{title}` in the template (matching the long-standing behavior of the `%s` branch); the previous single-substitution behavior was undocumented and unlikely to have been depended on. (`src/utils/title.ts`)

- **`OpenGraphImage.secureUrl` / `OpenGraphVideo.secureUrl` / `OpenGraphAudio.secureUrl` skipped URL validation** - The explicit `secureUrl` field on each typed OG media item was previously written to `og:image:secure_url` / `og:video:secure_url` / `og:audio:secure_url` without going through the `isUrlValid` helper. The primary `url` was validated, but a malformed `secureUrl` (e.g., a value pulled from a CMS field that happened to be `http://[invalid`) slipped straight into the DOM as a `<meta property="og:image:secure_url" content="http://[invalid">` tag. Now, when `validateUrls` is `true`, the `secureUrl` value is checked with `isUrlValid` before being emitted; an invalid value logs a dev warning (`Invalid URL provided for og:*:secure_url: …`) and the corresponding `og:*:secure_url` meta is skipped, while the rest of the image/video/audio entry (primary `url`, width/height/alt/type) still emits normally. The fallback `https:`-derived `secure_url` path (when no explicit `secureUrl` is provided) is unaffected because the primary `url` was already validated upstream. (`src/useSEO.ts`)
- **`additionalMetaTags` whitespace-only `name`/`property`/`httpEquiv` bypassed the empty-trio guard** - The previous guard rejected only the case where ALL THREE key fields were strictly falsy. A tag like `{ name: '   ', content: 'foo' }` (whitespace-only single field) bypassed the guard, built the key as `{ name: '   ' }`, and produced a `<meta name="   ">` element with a syntactically valid but semantically meaningless identifier. The same shape applied for whitespace-only `property` or `httpEquiv`. The hook now trims each of `name`, `property`, and `httpEquiv` before the key dispatch and only considers non-empty trimmed values; if all three are empty/whitespace after trimming, the tag is skipped with a dev warning (`additionalMetaTags entry has no non-empty name/property/httpEquiv after trimming; skipping.`). When at least one field has content after trimming, the trimmed value is used as the identifier (so `{ name: '  theme-color  ' }` correctly produces `<meta name="theme-color">` rather than `<meta name="  theme-color  ">`). (`src/useSEO.ts`)
- **JSON-LD reuse path served stale content on the rare hash collision** - The incremental reconciliation Map keyed `<script type="application/ld+json">` elements by an FNV-1a hash of `JSON.stringify(data)`. Whenever the new render's hash matched a stored hash, the existing element was reused (re-appended to enforce document order, `data-seo-index` updated) but `textContent` was never re-written. If two semantically distinct payloads happened to share the same FNV-1a hash (extremely rare but possible), the DOM kept the stale payload from the previous render even though the caller intended a different one. The reconciliation Map now stores `{ element, content }` per slot, where `content` is the previously-rendered HTML-escaped JSON string. On the reuse path the new payload is re-serialized via the new `serializeJsonLdContent` helper and compared against the stored content; only when they differ (collision detected) does the hook write the new `textContent` and update the stored content. When the content matches exactly the DOM write is skipped, preserving the perf characteristic of incremental reconciliation. The new `serializeJsonLdContent(data, index)` helper in `src/utils/dom.ts` performs the same `JSON.stringify` + `escapeJsonForHtml` pipeline that `createJsonLdScript` uses (and `createJsonLdScript` was refactored to call it), so the two paths cannot drift. (`src/utils/dom.ts`, `src/useSEO.ts`)
- **`getCurrentSEO()` returned a SHALLOW copy — nested array/object mutations leaked into the internal snapshot** - The previous implementation did `return { ...lastSnapshotRef.current }`, which spreads only the top-level keys; nested arrays (`ogImages`, `additionalMetaTags`, `additionalLinkTags`, `structuredData`, `ogVideos`, `ogAudios`, `articleTags`, `hreflangs`, `ogLocaleAlternates`) and the objects inside them were live references to the internal snapshot ref. A consumer that called `getCurrentSEO().ogImages.push({ url: '…' })` (or mutated `structuredData[0]['@type']`, etc.) would mutate the internal snapshot ref, so a subsequent `getCurrentSEO()` would return the corrupted state — and the change-detection JSON serialization on the next render would be derived from a snapshot that no longer reflected what the hook actually had to apply. The snapshot returned by `getCurrentSEO()` is now a deep clone via `structuredClone(lastSnapshotRef.current)` (Node 17+ and all supported browsers per the README's browser-support matrix), with a `JSON.parse(JSON.stringify(snap))` fallback for environments where `structuredClone` is undefined — sufficient because `SEOProps` does not carry `Date`, `Map`, `Set`, or other non-JSON-serialisable values. The contract is now: "the snapshot is fully owned by the caller; mutate freely." (`src/useSEO.ts`)

- **JSON-LD `</script>` HTML-injection vector** - `createJsonLdScript` previously assigned `JSON.stringify(data)` directly to `script.textContent`. A structured-data string field containing the literal substring `</script>` would be parsed as the closing tag for the surrounding `<script>` element, allowing arbitrary HTML (and thus script) injection when structured data is built from CMS- or user-supplied values. The serialized JSON now has `<`, `>`, `&`, U+2028 and U+2029 escaped as `\uXXXX` Unicode escapes (the canonical safe-JSON-in-HTML pattern used by `serialize-javascript` and Next.js). The serialization is also wrapped in try/catch so circular references or `BigInt` values are logged via `logError` and the script is skipped instead of crashing the hook. (`src/utils/dom.ts`)
- **Selector injection / breakage from unescaped hreflang values** - The hreflang loop in `useSEO` interpolated `h.hrefLang` raw into the `keySelector` string (`[hreflang="${h.hrefLang}"]`). A value like `en"]><img>` corrupted the selector, threw `SyntaxError` from `document.querySelector`, and was silently swallowed by the surrounding try/catch — meaning the entire SEO effect aborted partway through. Now the hreflang value is escaped via `escapeSelectorValue` before being interpolated, and `escapeSelectorValue` is re-exported from `src/useSEO.ts`'s import list for that purpose. (`src/useSEO.ts`)
- **`getOrCreateMeta` silent footgun on empty key** - When called with `{}` (or `{ name: '', property: '', httpEquiv: '' }`), the function previously fell back to a generic `'meta'` selector and could overwrite (or create a duplicate of) whatever the first meta element in `<head>` happened to be. The function now returns `null` when no key field is non-empty, and its return type was widened to `HTMLMetaElement | null`. The internal `updateMetaInternal` callback and the public `updateMetaTag` method on the hook return both bail out when the key is empty; the public method also emits a dev warning so the misuse is visible. (`src/utils/dom.ts`, `src/useSEO.ts`)
- **`clearSEOTags` silently deleting user-authored elements** - `getOrCreateMeta`/`getOrCreateLink` may return a pre-existing user-authored element that the hook only mutated; the previous code added every returned element to the `addedElements` Set, so `clearSEOTags()` later removed it from the DOM — silent data loss for any `<meta name="description">` or `<link rel="canonical">` that the consumer authored before the hook mounted. The internal `updateMetaInternal` and `updateLinkInternal` callbacks now only track elements that carry the `data-use-seo="true"` marker (which `createMeta`/`getOrCreateMeta`/`getOrCreateLink` set ONLY on the create path). `clearSEOTags` itself was also hardened with a defense-in-depth marker check before removal. - **Stale `og:image*`, `og:locale:alternate`, and hreflang tags lingering after the prop shrinks or is unset** - The `removeMarkedElements` cleanup for these multi-value sections used to live INSIDE the `if (value?.length)` branch, so re-rendering with `ogImages: undefined` (or `[]`) left the previously-created tags in the document forever. Cleanup now runs unconditionally before the recreate loop. Selectors covered: `meta[property^="og:image"]` (which includes `og:image`, `og:image:width`, `og:image:height`, `og:image:alt`, `og:image:secure_url`, `og:image:type`), `meta[property="og:locale:alternate"]`, and `link[rel="alternate"][hreflang]`. - **`isUrlField` over- and under-matching** - The previous heuristic used substring matching on `'url'`/`'image'`/`'href'`/`'canonical'`, so it both produced false positives (`urltext`, `imagealt`, `thumbnailalt`, `hreflang`, `canonicaltitle`) and false negatives (`og:audio`, `og:video`, `twitter:image:src`, `twitter:url`, `twitter:player(:stream)`, `article:author/publisher`). It is now an allow-list of well-known SEO/Open-Graph/Twitter URL identifiers plus boundary-aware suffix matches for `url`/`href`/`src`/`image` (camelCase boundary or `:`/`_`/`-`/`.` separator). `hrefLang` correctly NO LONGER matches; `secureUrl`/`thumbnailUrl`/`coverImage` correctly DO. (`src/utils/validation.ts`)
- **`updateMetaTag` ignored `httpEquiv` for URL-field detection** - The public `updateMetaTag` derived its field-name as `key.property ?? key.name ?? ''`, so a call like `updateMetaTag({ httpEquiv: 'X-Frame-URL' }, 'http://[invalid')` skipped URL validation entirely, even though the value was clearly intended as a URL. The lookup now also considers `key.httpEquiv`. The new conservative `isUrlField` correctly leaves common HTTP-Equiv names (`refresh`, `Content-Type`, `default-style`) un-validated because their content is composite, not a bare URL. (`src/useSEO.ts`)
- **`additionalMetaTags` and `additionalLinkTags` bypassed `validateUrls`** - Custom meta tags whose `name`/`property`/`httpEquiv` matched a URL field (e.g., `additionalMetaTags: [{ property: 'og:image', content: 'http://[invalid' }]`) were added to the DOM unchecked, even with `validateUrls: true`. The same was true for `additionalLinkTags` href values: `updateLinkInternal` did validate, but the failure was logged with the wrong message context. - **BCP 47 fallback regex too narrow** - The fallback regex used by `normalizeLanguageTag` when `Intl.getCanonicalLocales` is unavailable rejected several valid tag forms: extension subtags (`en-US-u-ca-buddhist`, `en-t-en-latn`), private-use subtags (`en-x-private`, whole-tag `x-foo`), extlang subtags (`zh-cmn`, `zh-yue-Hant-HK`), and standalone variants (`sl-rozaj`, `de-1996`). - **Robots `{ index: true, follow: true }` silently dropped** - `RobotsObject` allowed `{ index: true, follow: true }` but the serializer only emitted the negative forms (`noindex`, `nofollow`); explicit positive intent produced an empty robots string and no `<meta name="robots">` tag, so users could not override a parent `<meta name="robots" content="noindex">` (e.g. one injected by Tag Manager) via the hook. The serializer in `src/utils/robots.ts` now treats `index` and `follow` as tri-state: `true` emits the positive directive (`index` / `follow`), `false` emits the negative directive (`noindex` / `nofollow`), `undefined` omits the directive entirely. The `googlebot` nested object honors the same semantics. The JSDoc on `buildRobots` and the README now document precedence explicitly: when both the `robots` prop and the deprecated boolean flags (`noindex`, `nofollow`, …) are passed, `robots` wins outright. (`src/utils/robots.ts`, `src/types.ts`, `README.md`)
- **`updateLinkTag` accepted unsafe inputs** - The public `updateLinkTag` would silently accept `rel=''`, `rel='   '`, or runtime-`null`/`undefined` `rel`, which would build a `link[rel=""]` selector and either match an unrelated link or create a useless empty `<link>` element. It would also accept `null`/`undefined` `href` (which the TS signature forbade but is reachable from JS callers), creating a `<link href="">` that the browser interprets as the document URL. The function now warns and no-ops in both cases, and the warning text is scoped to the rel value so the cause is easy to spot. The overload disambiguation was also tightened: the third argument's runtime type still drives the choice (object → modern, string → legacy), but when it is `null`/`undefined` we now also inspect the fourth argument — if it is a `boolean` we treat the call as the modern signature (so `updateLinkTag('canonical', 'https://x', undefined, true)` correctly applies `unique=true`), otherwise we fall through to the legacy signature with `type=undefined`. (`src/useSEO.ts`)
- **JSON-LD scripts re-created on every effect run regardless of which item changed** - The structured-data block previously called `removeMarkedElements('script[type="application/ld+json"]', …)` and then re-created EVERY `<script>` from scratch on each render where the effect ran. For long-form pages with multiple JSON-LD payloads (Article + BreadcrumbList + FAQ + Product), changing a single unrelated SEO prop (e.g. `description`) would tear down and re-create all of them, briefly dropping them from the DOM and forcing crawlers / consumers observing live mutations to re-parse everything. The hook now keeps a `Map<string, HTMLScriptElement>` keyed by a stable FNV-1a hash of each item's `JSON.stringify` output. On each effect run it (1) removes only scripts whose hash disappeared, (2) reuses existing `<script>` elements whose hash is unchanged (preserving Element identity — verified by tests via referential equality), (3) creates new `<script>` elements only for new hashes, and (4) re-appends in the new array order so document order matches the caller-supplied order even when the array is shuffled. The `data-seo-index` attribute is updated on reused elements so it reflects the new position. The hashing uses a tiny non-cryptographic FNV-1a (~10 lines, allocation-free, `Math.imul`-based) and the resulting base-36 string keys the Map. The HTML-escape pass that prevents `</script>` injection (T3) still runs on the rendered output — hashing is performed on the raw `JSON.stringify` so semantically identical payloads share a hash regardless of escape transformations. (`src/useSEO.ts`, `src/utils/dom.ts`)

## [0.2.0] - 2026-02-21

### Added

- **`titleSeparator` prop** - New `titleSeparator` property in `SEOProps` allows customizing the separator between title prefix/suffix and the base title. Defaults to `' | '`. (`src/types.ts`, `src/useSEO.ts`)
- **CSS selector sanitization** - New `escapeSelectorValue()` utility function in `src/utils/dom.ts` escapes special characters (`"`, `\`) in CSS selector attribute values, preventing malformed selectors when meta tag names or properties contain special characters.
- **URL validation for prop-based meta tags** - URLs passed through props (`ogImage`, `ogUrl`, `twitterImage`, `ogImages[].url`) are now validated when `validateUrls` is true. Previously only URLs set through `updateMetaTag()` and `updateLinkTag()` were validated. (`src/useSEO.ts`)
- **`removeMarkedElements` tracking** - `removeMarkedElements()` now accepts an optional `trackedElements` Set parameter to also remove cleaned-up elements from the tracking Set, preventing memory leaks. (`src/utils/dom.ts`)
- **18 new tests** covering all the changes below across `tests/utils/dom.test.ts`, `tests/utils/validation.test.ts`, and `tests/useSEO.test.tsx`.

### Fixed

- **Memory leak in `addedElements` Set** - When `removeMarkedElements` removed elements from the DOM (for og:locale:alternate, og:image, hreflang, JSON-LD, robots), the elements were not removed from the `addedElements` tracking Set. This caused the Set to grow unboundedly with stale references to detached DOM nodes, preventing garbage collection. All `removeMarkedElements` calls now pass the tracking Set for cleanup. (`src/useSEO.ts`)
- **`inferImageMimeType` hash fragment handling** - URLs with hash fragments (e.g., `image.jpg#section`) now correctly extract the file extension. The regex was updated from `/\.([a-z0-9]+)(?:\?.*)?$/i` to `/\.([a-z0-9]+)(?:[?#].*)?$/i`. (`src/utils/validation.ts`)
- **`additionalMetaTags` without key identifier** - Tags missing all key identifiers (`name`, `property`, `httpEquiv`) are now skipped. Previously, such tags would generate an empty CSS selector that could match any meta element, potentially overwriting unrelated meta tags. (`src/useSEO.ts`)
- **Missing `SEO_MARKER` on charset meta** - The charset meta element created by `ensureEssentialMeta()` now receives the `data-use-seo` marker attribute, consistent with all other elements created by the hook. (`src/utils/dom.ts`)
- **Misleading cleanup function comment** - The useEffect cleanup function (which was intentionally a no-op) had a misleading comment suggesting it cleaned up JSON-LD scripts. Replaced with an accurate comment explaining the intentional no-cleanup behavior for SPA navigation. (`src/useSEO.ts`)

### Changed

- **Hardcoded thresholds replaced with constants** - Warning thresholds in `useSEO.ts` (title length 30/60, description length 120/160, keywords count 10) and `src/utils/title.ts` (`validateTitleLength`, `validateDescriptionLength`, `validateKeywordsCount`) now use the exported constants (`MIN_TITLE_LENGTH`, `MAX_TITLE_LENGTH`, `MIN_DESCRIPTION_LENGTH`, `MAX_DESCRIPTION_LENGTH`, `MAX_KEYWORDS_COUNT`) instead of hardcoded values. This ensures the constants and actual behavior stay in sync.
